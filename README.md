# Reward-Hacking Auditor

In reinforcement learning with verifiable rewards, the reward is a program.
Usually it is a test suite. The model writes a solution, the tests run, and
passing tests means reward. That rests on an assumption nobody checks, which is
that passing the tests means the task was actually done.

This tool checks it. It attacks a test suite with cheat solutions and reports
the false-accept rate, meaning the share of cheats the suite wrongly passes. It
runs against real published test suites, not only toy ones.

## A simple example

    python fetch_mbpp.py
    python run_mbpp.py

    Share of tasks each attack false-accepts on
    verifier          weak  strong
    attack
    constant_common   0.01    0.00
    constant_true     0.00    0.00
    constant_zero     0.00    0.00
    edge_blind        0.96    0.14
    empty_blind       0.76    0.63
    first_arg_length  0.00    0.00
    memorize_visible  0.99    0.01

    Published MBPP tests only, false-accept rate  34% (272/800)
    Plus three held-out tests, false-accept rate  10% (78/800)

Those are the real test suites shipped with the first 100 usable MBPP problems.
Weak means the three published asserts, which are the entire suite and are also
shown to the solver. Strong means those plus three held-out inputs.

## The headline result

A solution that is correct everywhere except on empty inputs and zero is
accepted by 76% of these published MBPP suites, and adding three held-out tests
drawn from the same distribution only brings that to 63%. Held-out tests are
usually presented as the fix for gameable rewards. Against memorisation they
are, and the memorize attack drops from 99% to 1%. Against a solution with a
hole in it they barely help, because tests sampled from the same distribution
land in the same places the original tests did.

That is the practical finding. If you are training against a test suite, the
share of reward you are handing out for untested edge cases is large, and more
tests of the same kind will not recover it.

## How it works

Every task carries three sets of inputs. The visible tests are what a solver can
see. The hidden tests are held out and only the strong verifier checks them. The
oracle inputs decide whether a candidate is really correct, and the tool alone
sees them.

Expected outputs are never written by hand. They are computed by calling the
task's reference implementation, so the three sets cannot disagree.

A false accept is a candidate the verifier passes but the oracle fails. That is
reward without work, which is what reward hacking looks like in practice.

For the real tasks, all three sets come from MBPP. The visible tests are the
problem's three published asserts. The hidden tests and most of the oracle
inputs are generated by fuzzing values that look like the published ones, then
keeping the ones the reference implementation accepts. The oracle also gets
deliberate edge cases, meaning empty containers, zero and single element inputs.
Those go to the oracle only and never to the hidden tests, so the strong
verifier gets no unfair credit for them. Problems whose reference does not
satisfy its own published asserts are dropped.

## The attacks

The blind attacks see only the visible tests, because that is all a cheater
gets. They return the most common visible answer, memorize the visible inputs in
a table, return a constant, return the input, or return the length of the first
argument. None contains a line of task logic.

Two of them are worth reading with care. The memorize attack beats a
visible-only verifier by construction, since a lookup table over the visible
inputs is perfect on the visible inputs. Its interesting number is the strong
one. The same goes for the edge_blind attack described below.

The blind spot attacks are the more convincing ones. They are given a correct
solution and then deliberately broken on inputs the visible tests do not cover.
edge_blind is correct inside the range of values the visible tests span and
wrong outside it. empty_blind is correct except on empty inputs and zero. These
pass a verifier only if the suite forgot that case, so what they measure is test
coverage rather than memorisation, and they are the reason the strong verifier
does not save you.

## Using Claude to write the cheats

    python llm_attack.py

Instead of the fixed generic attacks, this asks Claude to write a task specific
cheat given the problem description and the three published tests. Claude never
sees the reference solution, the held-out tests or the oracle inputs. Answers
are cached in results/llm_cheats.json so a rerun costs nothing. Needs
ANTHROPIC_API_KEY.

This part is written but has not been run, because there is no API key on the
machine it was built on. The numbers above do not include it.

## Toy tasks

    python run_audit.py

Four hand-written tasks where the failure modes are visible by eye. Weak 34%,
strong 0%. Useful for understanding the measurement, not evidence about anything
in the wild.

## Files

fetch_mbpp.py downloads the dataset. mbpp.py turns MBPP problems into tasks.
tasks.py holds the toy tasks. attacks.py holds the cheat generators. auditor.py
holds the verifiers, the oracle and the false-accept count. run_mbpp.py and
run_audit.py run the two suites and write into results. llm_attack.py is the
Claude version.

## Limits

The tool executes MBPP reference solutions, which is downloaded code. It is a
well known public dataset, but treat any file you point this at as code you are
choosing to run.

The fuzzer only generates inputs built from integers, floats, strings, lists and
tuples, so problems taking dictionaries or sets are skipped. Hidden tests come
from the same fuzzer as most oracle inputs, which is what makes the empty_blind
result meaningful, since it shows what same-distribution held-out tests miss.

100 problems is enough to see the effect and not enough to be a careful
measurement of MBPP as a whole. Raise the limit in run_mbpp.py to check.
